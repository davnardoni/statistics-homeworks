From Wallet Seed to Ethereum Address: Hashing, Key Derivation and Cryptographic Primitives

1. Introduction

Cryptocurrency wallets use several cryptographic techniques to manage private keys, generate public keys and derive blockchain addresses. Although these operations are connected, they serve different purposes and cannot be replaced by a single algorithm.

In Ethereum, many software wallets use a mnemonic recovery phrase to generate a deterministic wallet. Starting from this phrase, the wallet can derive multiple private keys and their corresponding public keys and addresses.

The process involves several standards: BIP-39, BIP-32, BIP-44, secp256k1, Keccak-256 and EIP-55. The objective of this homework is to understand the role of each component, explore a practical example and discuss the relevant statistical and cryptographic properties.

2. Ethereum Wallet Derivation Pipeline

The following diagram summarizes the main steps used by a typical hierarchical deterministic Ethereum wallet, from its mnemonic phrase to the final checksummed address.

Mnemonic Phrase Human-readable recovery words
↓ BIP-39
Seed 512-bit binary value
↓ BIP-32 / BIP-44
Private Key Derived using an HD wallet path
↓ secp256k1
Public Key Elliptic-curve scalar multiplication
↓ Keccak-256
Ethereum Address Last 20 bytes of the hash
↓ EIP-55
Checksummed Address Mixed-case hexadecimal representation

2.1 BIP-39: Mnemonic Phrase and Seed

BIP-39 defines a method for representing randomly generated entropy as a human-readable sequence of words, typically 12 or 24 words. This makes wallet backup and recovery easier than storing a long binary secret.

The mnemonic is converted into a 512-bit seed using PBKDF2 with HMAC-SHA512, 2048 iterations and a salt consisting of the string "mnemonic" followed by an optional passphrase.

The initial mnemonic is generated from random entropy and includes checksum information. The subsequent mnemonic-to-seed operation is deterministic: the same mnemonic and passphrase always produce the same seed.

2.2 BIP-32: Hierarchical Deterministic Wallets

BIP-32 defines how to derive a hierarchy of cryptographic keys from a single master seed. It uses HMAC-SHA512 to generate master key material and derive child keys through a hierarchical structure.

This allows a wallet to generate many accounts without independently creating and backing up a new random private key for every address.

2.3 BIP-44: Derivation Paths

BIP-44 specifies a common structure for HD wallet derivation paths. For Ethereum, one widely used path is:

m/44'/60'/0'/0/0

Here, 44' identifies the BIP-44 purpose, 60' identifies Ethereum, 0' is the account index, the following 0 is the change branch, and the final 0 selects the address index. An apostrophe indicates hardened derivation.

Changing the address index allows us to derive multiple different addresses from the same seed. The exact derivation paths used by wallet software can vary.

2.4 secp256k1: Public-Key Cryptography

Once a private key has been derived, the public key is generated through elliptic-curve scalar multiplication, as studied in Homework 1:

Q = kG

Ethereum uses the secp256k1 elliptic curve. The private key is a scalar, while the public key is a point on the elliptic curve. The security of the operation is based on the computational difficulty of solving the Elliptic Curve Discrete Logarithm Problem.

This public/private key relationship also supports digital signatures, which allow Ethereum users to authorize transactions without revealing their private keys.

2.5 Keccak-256: Ethereum Address Generation

An Ethereum externally owned account address is obtained by hashing the 64-byte uncompressed public-key coordinates (excluding the 0x04 format prefix) with Keccak-256.

Keccak-256 produces a 256-bit hash. Ethereum takes the last 20 bytes, equivalent to 160 bits, as the account address.

Address = last 20 bytes of Keccak-256(Public Key)

The address is displayed as 40 hexadecimal characters preceded by "0x". Hashing the public key is distinct from the elliptic-curve multiplication that generated it.

2.6 EIP-55: Address Checksum

EIP-55 introduces a mixed-case representation of Ethereum addresses to help detect accidental typing errors.

It applies Keccak-256 to the lowercase hexadecimal address string and uses bits of the resulting hash to determine which alphabetical hexadecimal characters should be uppercase.

This process does not create a new address or change its underlying 160-bit value. It only changes its textual representation to provide error-detection information.

4. Different Cryptographic Operations

The wallet pipeline combines several distinct operations. It is important not to confuse random key generation, deterministic key derivation, public-key cryptography, hashing, checksums and encoding.

Operation Purpose Example
Key generation Create new unpredictable secret material Random entropy for a wallet
Key derivation Derive keys deterministically from a seed BIP-32 / BIP-44
Public-key cryptography Relate private and public keys; enable signatures secp256k1
Hashing Produce a fixed-size cryptographic digest Keccak-256
Checksum Detect some accidental errors EIP-55
Encoding Represent information in a readable format Mnemonic words, hexadecimal address

For example, encoding a value into hexadecimal does not make it cryptographically secure. Similarly, a checksum is designed to detect errors, not to provide the same security guarantees as a digital signature.

5. Statistical Properties

We can examine some elementary statistical properties of the addresses derived from the same mnemonic using different BIP-44 indices.

In this experiment, we derive eight addresses using indices 0 through 7. We then count their zero and one bits, examine hexadecimal digit frequencies, and compare consecutive addresses using their Hamming distance.

Run the experiment to see the results.

5.1 Bit Distribution and Uniformity

An Ethereum address consists of 160 bits. For eight addresses, we obtain a total of 1280 output bits. Counting zeros and ones provides a simple measure of observed bit balance.

For a uniform random bit string, each bit has probability 1/2 of being zero or one. Therefore, we may expect approximately equal frequencies in a sufficiently large sample.

However, observing balanced bits in a small sample does not prove that the key-derivation process or the hash function is secure.

5.2 Hexadecimal Digit Distribution

Each Ethereum address contains 40 hexadecimal digits. In an ideal uniform distribution, each of the 16 possible symbols would have equal probability.

We can count the frequency of each digit in the derived addresses and compare the observed values. Since we use only eight addresses, random fluctuations are expected.

5.3 Avalanche-like Behaviour

To explore the sensitivity of the output to changing derivation indices, we compare consecutive addresses with the Hamming distance.

For two independent uniformly distributed 160-bit strings, the expected Hamming distance is 80 bits. We use this value as a statistical reference, not as a security test.

Importantly, changing a derivation index is not equivalent to flipping one input bit of Keccak-256. Therefore, this experiment does not directly measure the strict avalanche criterion of the hash function.

The essential cryptographic properties of the pipeline include strong initial entropy, secure key derivation, the difficulty of recovering a private key from a public key, and the preimage resistance of the hash function. Output-frequency experiments alone cannot establish these properties.

6. Historical Context

The cryptographic primitives used in Ethereum wallets were not developed simultaneously. They combine ideas introduced over several decades, each solving a different problem.

Year Technology Contribution
1977 RSA Public-key cryptography
2001 SHA-2 / SHA-512 Standardized cryptographic hashing
2012 BIP-32 Hierarchical deterministic wallets
2013 BIP-39 Mnemonic recovery phrases
2014 BIP-44 Standardized multi-account paths
2015 SHA-3 NIST standard based on Keccak
2016 EIP-55 Mixed-case checksum addresses

SHA-512 vs Keccak-256 / SHA-3

SHA-512 belongs to the SHA-2 family and uses a different internal construction from Keccak. It produces a 512-bit output and is used within HMAC-SHA512 for key derivation in BIP-39 and BIP-32.

Keccak was selected as the foundation of the SHA-3 standard, finalized by NIST in 2015. Ethereum uses Keccak-256 for several hashing operations, including address generation.

Although Keccak-256 and SHA3-256 are closely related, they are not identical. The standardized SHA3-256 uses a different padding and domain-separation convention from the Keccak-256 variant used by Ethereum. Consequently, the two functions generally produce different digests for the same input.

7. Discussion and Conclusions

The Ethereum wallet pipeline illustrates why a single algorithm cannot replace all the cryptographic mechanisms involved in wallet creation and account management.

BIP-39 provides a practical recovery mechanism and converts the mnemonic into a seed. BIP-32 and BIP-44 organize deterministic key derivation. secp256k1 establishes the mathematical relationship between private and public keys, while Keccak-256 is used to derive Ethereum addresses. Finally, EIP-55 adds error-detection information through mixed-case encoding.

These components provide complementary functions. Key derivation manages multiple accounts, elliptic-curve cryptography enables digital signatures, cryptographic hashing processes data into fixed-size digests, and checksums help detect mistakes in address transcription.

Conclusion

This homework examined the main stages involved in deriving an Ethereum address from a mnemonic recovery phrase. The practical experiment demonstrated how a single mnemonic can generate multiple deterministic accounts.

The statistical exploration considered bit frequencies, hexadecimal digit distributions and Hamming distances between derived addresses. These measurements illustrate observable output properties, but they do not independently prove cryptographic security.

The central conclusion is that secure Ethereum wallet operation depends on combining several cryptographic techniques, each designed for a specific purpose.
